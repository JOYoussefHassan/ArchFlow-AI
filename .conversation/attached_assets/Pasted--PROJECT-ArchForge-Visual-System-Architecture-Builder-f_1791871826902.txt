# PROJECT: ArchForge — Visual System Architecture Builder for Vibe Coding

## 1. Your role

Act as a principal software architect, senior systems engineer, expert visual editor developer, interaction designer, and senior vanilla JavaScript engineer.

Build a complete, attractive, highly interactive website called **ArchForge**.

The purpose of this application is to help a junior software developer design complete business systems without already having the knowledge of a senior software architect.

The user must be able to visually design systems containing:

- Web applications.
- Mobile applications.
- Desktop applications.
- Frontend applications.
- Backend services.
- API endpoints.
- Databases.
- Reusable core packages.
- Service inheritance and composition.
- AI services.
- Workflow automation.
- Message queues.
- External providers.
- Cloud infrastructure.
- Local servers.
- Multiple isolated or connected networks.
- Requests, responses, events, and data synchronization.

The application must transform the visual architecture into a structured specification, dependency-aware implementation plan, and a collection of prompts for AI coding agents.

This is an architecture editor, not a generic diagram editor.

## 2. Mandatory delivery requirements

Deliver the complete application as one file:

index.html

Use only:
- HTML5.
- CSS3.
- Vanilla JavaScript.
- SVG for the architecture canvas, nodes, connectors, and arrow routing.

No React, Vue, Angular, TypeScript compilation, npm, or build process.

The application must run by opening index.html in a modern browser.

Use localStorage or IndexedDB for local project persistence. Prefer localStorage for the initial implementation if the project size remains reasonable.

CDN libraries are optional, but the core editor must remain functional without external libraries. Do not use a diagramming library that prevents implementing the custom interaction and routing behavior described below.

Do not require a backend or AI API key for core functionality.

Do not fake live AI capabilities. Build a rule-based architect engine and an extensible interface for a future real AI provider.

Deliver actual working source code, not a mockup, pseudocode, or partial implementation.

## 6. Correct wire and arrow routing engine

THIS IS A CORE REQUIREMENT.

The connectors must behave like carefully routed electrical wires in an apartment distribution board.

Do not implement connections as arbitrary straight lines between node centers.

Create a dedicated SVG-based connector engine.

### A. Connector anchors

Every node should have visible or discoverable connection anchors.

Support:
- Top.
- Right.
- Bottom.
- Left.
- Named interface ports.
- Endpoint-specific ports.
- Required-input ports.
- Provided-output ports.

For backend services, allow connections to individual endpoints rather than connecting only to the center of the service.

When creating a connection, highlight compatible ports.

Prevent a connector from terminating at the wrong endpoint.

### B. Orthogonal wire routing

Use Manhattan routing by default: horizontal and vertical segments with 90-degree bends.

Wires must:
- Start at the selected source port.
- End at the selected target port.
- Avoid passing through node rectangles.
- Minimize unnecessary bends.
- Minimize crossings.
- Avoid overlapping labels.
- Maintain readable spacing between parallel wires.
- Recalculate when connected nodes move.
- Remain connected during zooming and panning.
- Use stable routing where possible instead of jumping unpredictably.

Implement a routing algorithm using:
- Source and target port positions.
- Port exit directions.
- Node obstacle rectangles.
- Configurable routing clearance.
- Bend penalties.
- Crossing penalties where practical.
- A fallback route when no preferred path is found.

A grid-based A* router or a robust orthogonal waypoint router is acceptable.

Use rounded corners sparingly so wires still look precise.

If no valid route can be found, display a visible warning and use a fallback path that does not conceal the problem.

### C. Parallel connections and crossings

When multiple wires connect the same pair of nodes:
- Assign different lanes.
- Offset parallel wires.
- Prevent overlapping labels.
- Make each wire individually selectable.

When wires cross:
- Make crossings visually distinguishable.
- Use line jumps or bridge arcs where practical.
- Never imply that crossing wires are connected unless an explicit junction exists.

Allow users to manually insert or move routing waypoints.

Provide a "Reset route" action to restore automatic routing.

### D. Directional communication

Every connector must represent a real architectural relationship.

Store:
- Connection ID.
- Source node ID.
- Source port ID.
- Target node ID.
- Target port ID.
- Connection type.
- Protocol.
- Label.
- Direction.
- Request contract.
- Response contract.
- Authentication.
- Timeout.
- Retry policy.
- Error behavior.
- Sync/async classification.

The source and target are authoritative. Do not infer direction from the visual arrowhead alone.

### E. Request and response visualization

Support two display modes.

**Mode 1: Separate request and response wires**

Example:

Frontend -- HTTP POST /orders --> Order API

Frontend <-- HTTP 201 + OrderResponse -- Order API

The request and response must use separate, individually labeled paths when both are explicitly modeled.

**Mode 2: Combined bidirectional exchange**

Render a request/response pair as one logical interaction with two directional arrows or a clearly marked bidirectional connection.

Allow users to switch between these modes.

A request and response must share a logical interaction ID when they belong to the same operation.

Do not count a response as an unrelated API call.

For synchronous request/response protocols, show:
- Request method and path.
- Request schema.
- Response status codes.
- Response schema.
- Timeout.
- Error response.

For asynchronous communication, model events, acknowledgements, replies, and correlation identifiers separately when applicable.

### F. Wire editing

When selecting a wire, show:
- Source.
- Destination.
- Source interface.
- Target interface.
- Protocol.
- Request/response mode.
- Direction.
- Label.
- Authentication.

- Error behavior.

Support reconnecting wires by dragging their endpoints to another compatible port.

## 7. Service-to-endpoint architecture

A backend service and its endpoints must be modeled separately.

For example:

Web Frontend
    |
    | HTTPS request
    v
Pharmacy API Service
    |
    +---- POST /api/sales
    |
    +---- GET /api/drugs/{id}
    |
    +---- POST /api/auth/login

The endpoints are individually selectable nodes or first-class interface objects.

Support both representations:
- Endpoints displayed as child blocks inside a service.
- Endpoints displayed as separate blocks connected to their parent service.

Users can choose the preferred visualization.

An endpoint must have:
- Stable ID.
- Parent service ID.
- Operation ID.
- HTTP method or protocol operation.
- Path or operation name.
- Description.
- Request schema.
- Response schemas.
- Error responses.
- Authentication requirements.
- Authorization permissions.
- Validation rules.
- Rate limits.
- Timeout.
- Versioning.
- Idempotency requirements where relevant.

An endpoint must not accidentally become a standalone deployed service just because it is represented by its own node.

The service owns the implementation and runtime; the endpoint defines an interface exposed by that service.

Support connections such as:

Frontend -> POST /api/sales
POST /api/sales -> Sales Service
Sales Service -> Inventory Service
Inventory Service -> Inventory Database

For clarity, either the endpoint connects to its owning service, or the parent-child relationship is displayed internally, depending on the chosen visualization mode.

The underlying data model must preserve the distinction in both cases.

Generate implementation prompts using the exact endpoint contracts.
